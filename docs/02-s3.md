## 1. Objetivo

Crear el almacenamiento del frontend estático **sin servidores** y **sin exponerlo públicamente**:

- entender qué es object storage y cómo funciona S3;
- crear un bucket privado con las protecciones de seguridad activas;

## 2. Conceptos clave

### 2.1 Tipos de almacenamiento

| Tipo | Cómo funciona | Analogía | Servicio AWS |
|---|---|---|---|
| **Block storage** | Disco "crudo" montado en un servidor | El SSD de una computadora | EBS |
| **File storage** | Sistema de archivos compartido por red | Una carpeta compartida | EFS |
| **Object storage** | Objetos completos identificados por una clave, accesibles por API HTTP | Un diccionario `{clave: archivo}` detrás de una API REST | **S3** |

Características de object storage:

- **Un objeto no se edita parcialmente.** Para cambiar una línea de `index.html` se sube el archivo completo, que reemplaza al anterior.
- **No existen carpetas reales.** `js/app.js` es una **clave** que contiene una barra. La consola muestra "carpetas" a partir de esos **prefijos**.
- **Se accede por HTTP**, a través de la API de S3 (`PUT`, `GET`, `DELETE`).

### 2.2 Vocabulario

| Término | Qué es | Ejemplo |
|---|---|---|
| **Bucket** | Contenedor de objetos. Los datos viven en **una región**, pero el nombre es **único en todo el mundo** | `cloud-sec-checklist-frontend-<sufijo>` |
| **Object** | Archivo + metadatos (tipo de contenido, fecha, etc.) | `index.html` |
| **Key** | Nombre completo del objeto dentro del bucket | `js/app.js` |
| **Prefix** | Parte inicial de la key, que la consola muestra como "carpeta" | `js/` |

### 2.3 Protecciones de seguridad de un bucket

| Protección | Valor por defecto actual | Qué hace |
|---|---|---|
| **Block Public Access (BPA)** | ✅ Activado (4/4) | Impide que ACLs o bucket policies hagan público el bucket, aunque alguien lo intente |
| **Object Ownership** | *Bucket owner enforced* (ACLs desactivadas) | Los permisos se gestionan solo con policies |
| **Default encryption** | ✅ SSE-S3 (AES-256) | Todo objeto se guarda cifrado en disco con claves gestionadas por AWS |
| **SSE-C bloqueado** | ✅ Bloqueado | Impide subir objetos cifrados con claves aportadas por quien los sube |

**Las 4 configuraciones de BPA:**

| Configuración | Qué bloquea |
|---|---|
| `BlockPublicAcls` | Que se apliquen ACLs públicas nuevas |
| `IgnorePublicAcls` | Que tengan efecto ACLs públicas existentes |
| `BlockPublicPolicy` | Que se guarde una bucket policy pública |
| `RestrictPublicBuckets` | Que una policy pública existente dé acceso a cualquiera |

**¿Por qué bloquear SSE-C?** Con SSE-C, quien sube el archivo envía su propia clave y AWS no la guarda. Se usó en ataques de ransomware: un atacante con credenciales robadas reescribía los objetos cifrándolos con **su** clave, y la víctima perdía el acceso a sus propios datos. Por eso AWS lo bloquea por defecto en los buckets nuevos.

### 2.4 Identity-based vs. resource-based policies

| Tipo | Dónde se adjunta | Qué responde | Ejemplo |
|---|---|---|---|
| **Identity-based** | A un usuario, grupo o rol | "¿Qué puede hacer **esta identidad**?" | El grupo `Admins` tiene `AdministratorAccess` |
| **Resource-based** (en S3: **bucket policy**) | Al **recurso** | "¿**Quién** puede acceder a este recurso?" | Solo CloudFront puede leer este bucket |

**Analogía:** la identity-based es la **credencial que lleva la persona**. La resource-based es la **lista pegada en la puerta**.

- En una resource-based policy, quien recibe el acceso se indica en el campo **`Principal`**.
- La bucket policy **vive dentro del bucket**: si se borra el bucket, se borra la policy.
- Una policy de grupo **es independiente de los usuarios**: si se borra un usuario, el grupo y su policy siguen existiendo.

### 2.5 Defensa en profundidad: deny by default + BPA

**Caso 1 — Request anónima desde un navegador:**

```text
GET https://<bucket>.s3.us-east-1.amazonaws.com/index.html   (sin credenciales)
   │
   ├── ¿Alguna policy permite el acceso anónimo?   → No → deny by default
   └── Aunque existiera, BPA la bloquearía
   ▼
403 AccessDenied
```

**Caso 2 — Un admin intenta guardar una bucket policy pública (`"Principal": "*"`):**

```text
   ├── IAM: ¿el admin puede modificar la policy?   → Sí (AdministratorAccess)
   └── BPA: ¿la policy hace público el bucket?     → Sí → ❌ RECHAZADA
```

BPA es una protección **del recurso** que actúa **además** de los permisos de quien hace la acción. Para hacer público el bucket habría que desactivar BPA a propósito.

**Detalle:** S3 responde `AccessDenied` también ante objetos que **no existen** (si quien pregunta no tiene permiso para listar). Así se evita que un atacante descubra qué archivos existen probando nombres (**enumeración**).

### 2.6 ARN (Amazon Resource Name)

Identificador único de cualquier recurso en AWS. Las policies lo usan para indicar **sobre qué recurso** aplican.

```text
arn : partición : servicio : región : cuenta : recurso
```

| ARN | Región | Cuenta | Motivo |
|---|---|---|---|
| `arn:aws:iam::<cuenta>:user/<admin-user>` | vacía | presente | IAM es global |
| `arn:aws:s3:::cloud-sec-checklist-frontend-<sufijo>` | vacía | vacía | El nombre del bucket es único globalmente y alcanza para identificarlo |

**Prefijos de IDs útiles:**

| Prefijo | Qué identifica |
|---|---|
| `AIDA...` | IAM user |
| `AKIA...` | Access key de largo plazo |
| `ASIA...` | Credencial temporal (STS) |

## 3. Decisiones técnicas

| # | Decisión | Alternativas evaluadas | Motivo |
|---|---|---|---|
| D9 | Frontend en **S3 privado + CloudFront con OAC** | S3 static website hosting público; AWS Amplify Hosting; GitHub Pages / Netlify | HTTPS, bucket privado y caché global. La opción pública obliga a desactivar BPA y solo ofrece HTTP: **la propia aplicación le daría FAIL a su bucket**. Amplify oculta lo que se quiere aprender; GitHub Pages queda fuera de AWS |
| D10 | **Versioning desactivado** en el bucket del frontend | Versioning activado | El historial del frontend ya está en Git. Cada versión guardada se cobra |
| D11 | Tag `Project = cloud-security-checklist` en todos los recursos | Sin tags | Permite encontrar todos los recursos del proyecto, analizar costos y verificar su eliminación |
| D12 | Bucket creado **manualmente** en esta etapa | Crearlo directamente con CDK | Primero entender cada opción en la consola. En la etapa de CDK se recrea como código y se elimina el bucket manual |

> **Contexto para entrevistas:** el frontend vive en un bucket S3 privado, con Block Public Access activado, y se sirve solo a través de CloudFront usando Origin Access Control. Descarté el static website hosting público porque obligaba a desactivar Block Public Access y no soporta HTTPS: en un proyecto de seguridad cloud, el propio despliegue tenía que pasar los mismos controles que la aplicación evalúa.

## 4. Configuración realizada

### 4.1 Bucket

| Opción | Valor | Por qué |
|---|---|---|
| Bucket type | General purpose | *Directory buckets* son para almacenamiento de alto rendimiento, no necesario |

| Object Lock | Disabled | Impediría borrar objetos y limpiar el proyecto |
| Bucket policy | Vacía | Se agrega en la Etapa 3 para CloudFront |
| Tags | `Project = cloud-security-checklist` | D11 |

### 4.3 AWS CloudShell

Para usar la AWS CLI **sin crear access keys** se usa **AWS CloudShell**: una terminal en el navegador que usa las credenciales temporales de la sesión de consola.

| Característica | Detalle |
|---|---|
| Identidad | La del usuario logueado en la consola, con sus mismos permisos |
| Costo | Sin costo adicional |
| Alcance | Regional (se usa en `us-east-1`) |
| Almacenamiento | `$HOME` persistente pequeño, que se elimina tras un período prolongado sin uso |

**Dos familias de comandos para S3:**

| | `aws s3 ...` | `aws s3api ...` |
|---|---|---|
| Nivel | Alto nivel (`ls`, `cp`, `sync`) | Una operación exacta de la API de S3 |
| Uso | Subir y listar archivos | Leer configuraciones exactas |

Las operaciones de `s3api` usadas en esta etapa son **las mismas que la aplicación ejecutará con boto3** en los checks automáticos.

## 7. Relación con Cloud Security

Dos de los checks que implementará la aplicación evalúan exactamente lo configurado en esta etapa:

| Check de la aplicación | Operación que usará (boto3) | Estado del bucket del proyecto |
|---|---|---|
| S3 Block Public Access | `get_public_access_block` | ✅ PASS |
| S3 Encryption | `get_bucket_encryption` | ✅ PASS |

**Least privilege para esos checks:** el rol de la Lambda que los ejecute necesitará solo permisos de **lectura** (`s3:GetBucketPublicAccessBlock`, `s3:GetEncryptionConfiguration`, `s3:ListAllMyBuckets`). Nunca permisos de escritura como `s3:PutBucketPublicAccessBlock`: si el código tuviera un bug o se robaran sus credenciales temporales, con permisos de solo lectura no podría desactivar ninguna protección.

| Prefijo de acción | Tipo | ¿Para la Lambda de checks? |
|---|---|---|
| `Get*`, `List*`, `Describe*` | Lectura | ✅ |
| `Put*`, `Create*`, `Delete*` | Escritura | ❌ |

## 8. Cómo revertir esta etapa

| Paso | Consola | CLI (CloudShell) |
|---|---|---|
| 1. Vaciar el bucket | Bucket → *Empty* → confirmar | `aws s3 rm s3://<BUCKET> --recursive` |
| 2. Borrar el bucket | Bucket → *Delete* → escribir el nombre | `aws s3api delete-bucket --bucket <BUCKET>` |
| 3. Verificar | El bucket no aparece en la lista | `aws s3 ls` no lo muestra |

> ⚠️ Estos comandos **borran datos de forma permanente** (sin versioning no hay recuperación). No ejecutarlos hasta la etapa de limpieza o de migración a CDK.

## 9. Cosas que NO se deben hacer

- ❌ Desactivar Block Public Access para "probar rápido".
- ❌ Agregar una bucket policy con `"Principal": "*"`.
- ❌ Activar Object Lock en un bucket de prueba.
- ❌ Usar el ID de cuenta o datos personales en el nombre del bucket.
- ❌ Dar permisos de escritura (`Put*`) a componentes que solo necesitan leer.
